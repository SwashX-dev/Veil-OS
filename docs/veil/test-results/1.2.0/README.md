## What was verified

**The black-screen-then-power-off bug (1.1.0).** The cause was Veil's own
session script, which powered the machine off whenever the compositor stopped.
In a VM, killing the compositor (SIGSEGV) while unlocked restarts the desktop
with software rendering, with no greeter and no power-off. Killing it while the
screen is locked restores the lock on the new desktop, and unlocking clears the
state. Six rapid losses still end in a normal shutdown. The emergency shutdown
and the loss shutdown print their reason on screen. **Why the compositor stops
on the reporter's hardware is still unknown**; see "Not tested".

**VPN before Tor** (WireGuard server in a second VM, endpoint reachable only
through Veil's firewall-mark rule):

- Tor bootstraps through the tunnel (12 s) and traffic exits through Tor.
- Tor's sockets originate from the VPN address.
- A 3-minute soak with repeated Tor traffic put **0 TCP packets** on the
  physical interface; only WireGuard UDP left the machine.
- Fail-closed: with the VPN server down, with the WireGuard interface removed
  (Tor's route is a blackhole), and while Tails reloads its firewall, nothing
  went out directly.
- Network Guard's `vpn.before_tor` check verified the rules.
- Disconnecting removes every rule and Tor connects directly again.

Two bugs found by this testing were fixed before release: WireGuard's encrypted
packets inherit the owner of Tor's inner packets, so the owner-based reject had
to come after the marked-UDP accept; and the first handshake was sent before
the firewall rule existed and arrived up to 25 s late.

An earlier test run (before those fixes) saw 2 TCP packets on the physical
interface once, in a 25 s window. It did not recur in four later runs, including
the soak, and the capture was not kept, so its cause is **unexplained**.

**Safe Graphics.** The first design (`nomodeset`) was tested and found
unusable: Tails' kernel has no firmware-framebuffer DRM driver, so no Welcome
Screen can start. The boot entry now uses `veil.safe-graphics
nouveau.noaccel=1 nouveau.runpm=0`. Detection of nouveau, `veil.safe-graphics`
and `veil.gpu-rendering` is unit-tested against fake `/sys/class/drm` trees.

**Privacy Center:** TCP timestamps off; idle lock (never locks without a
password; locks and unlocks with one); clipboard clearing; camera and
microphone kill switches (blocking needs no password, unblocking needs
authorization); polkit policy; diagnostics report; Tor Browser starts at the
Safest level; emergency shutdown hotkey; offline upscaling of video to 1080p
(Lanczos) and 1440p (FSRCNNX neural shader); Veil Player in safe graphics plays
with GPU video output, and the neural shader runs only in the enhanced preset.

## Not tested

- **No physical hardware.** The bug that started this release happened on real
  hardware (an NVIDIA laptop). The restart, safe-graphics and power-management
  changes are verified only in virtual machines, and **nouveau itself was never
  run**: the VMs have no NVIDIA GPU.
- **Real GPUs** for Veil Player's normal mode (GPU render node): untested; the
  normal-boot privacy run reports it as untested. Real-time 4K upscaling speed
  is unmeasured.
- Proton VPN itself: tested with a standard WireGuard server and a configuration
  in Proton's file format, not with Proton's servers.
- Tor Browser's Safer level, and the camera/microphone switches against real
  devices (a virtual camera and a virtual audio card were used).
- Wi-Fi, Secure Boot, battery effects of `nouveau.runpm=0`.
- An in-place upgrade from earlier releases. Re-flash instead.
- Reproducibility of the image build.
- Under load (several VMs at once) the test harness sometimes times out; those
  runs were repeated alone and all passed. Boot-time figures from loaded runs
  (56.5 s to the Welcome Screen) are not comparable with earlier releases.

This is a **prerelease**: do not rely on it where your safety depends on it.
